Project Structure (EDS Standards)

~2 hrs

Learning outcomes: Understand the AEM Boilerplate layout, how Git/GitHub connects to preview/live, and the role of each folder and file in a project.

a. File / Folder Organization

  • blocks/<blockname>/ — block code: _<blockname>.json (UE partial model rules), <blockname>.js, <blockname>.css
  • styles/ — styles.css (LCP minimal), lazy-styles.css (below fold), fonts.css
  • scripts/ — aem.js (core AEM lib, do not modify), scripts.js (global utilities), delayed.js (delayed-phase loading)
  • models/ — aggregate files: component-definitions.json, component-models.json, component-filters.json
  • Root: head.html, 404.html, .hlxignore

b. Core Setup Commands

  • npm install -g @adobe/aem-cli — install the AEM CLI globally
  • git clone <repo> then npm install
  • aem up — runs local dev at http://localhost:3000 (leave running in the background)
  • npm run lint — run eslint (airbnb-base) + stylelint before every PR
  • npm run build:json — aggregate per-block JSON into component-*.json
🧪 Hands-on Lab 1 Fork adobe-rnd/aem-boilerplate-xwalk, install AEM Code Sync bot, run aem up, and confirm your local site loads at http://localhost:3000. Modify styles.css and observe live reload.

Block & Component Modeling

~3 hrs

Learning outcomes: Define the block authoring contract, wire it up for Universal Editor, and follow content-modeling guidelines that keep blocks intuitive for authors.

a. Authoring Contract (Content-First)

  • Every block is authored as a table. First row = block name; body rows/cells define the content contract.
  • Start with the content in a Word/Google Doc before writing code — validate the structure with authors.
  • Same table contract works for both Document-based and Universal Editor authoring.

b. Universal Editor Integration

Each block ships three JSON files that get aggregated into project-level manifests via npm run build:json:

  • _<blockname>.json → block definition (template + default content) → aggregated into component-definitions.json
  • _<blockname>.json → field model (richtext, text, select, image…) → aggregated into component-models.json
  • Filter entry → controls where the block is allowed inside sections → aggregated into component-filters.json
Three-phased block dev (recommended by Adobe): 1️⃣ Define definition + model and ship to prod → 2️⃣ Author creates content with the new block → 3️⃣ Implement decorate() + CSS.

c. Guidelines

  • Max 3–4 columns per block table — keep it authorable.
  • 1st fold = use existing Blocks, not new experimental ones (avoid LCP regressions).
  • Prefer variant classes (block options like quote (dark, wide)) before creating a brand-new block.
  • Never nest blocks — very confusing for authors.
  • Use moveInstrumentation() whenever DOM is restructured so UE editing stays intact.

Block Decoration (Advanced Techniques)

~3 hrs

Learning outcomes: Master the decorate() pattern, write scoped mobile-first CSS, and understand the E-L-D three-phase loading architecture.

a. The Decorate Function (JS)

Every block's <blockname>.js exports a default async function. Typical pattern:

  • Load dependencies — loadScript() / loadCSS() only when needed by this block
  • Extract configuration from the raw table rows/cells (the authoring contract)
  • Transform DOM — replace nested <div>s with the semantic structure your CSS needs (preserve data-aue-*)
  • Add event listeners for interactivity

b. Scoped Styling (CSS)

  • Mobile-first — base styles = mobile; extend with min-width media queries only.
  • Standard breakpoints: 600px, 900px, 1200px — never mix min-width and max-width.
  • Isolate every selector to the block class (e.g. .block.quote blockquote { … }) — no bleed into other blocks.
  • Avoid {blockname}-container selectors — use the block class itself or its section wrapper.
  • Never use !important except in truly exceptional cases; leverage ARIA attributes for semantic styling hooks.

c. Three-Phase Loading Architecture (E-L-D)

The entry point is loadPage() in scripts.js, which orchestrates three phases:

Phase E — Eager Everything needed to render the LCP: decorate DOM, load first section + LCP image + block JS/CSS. Keep payload < 100 KB. Body starts hidden to avoid CLS.
Phase L — Lazy Header, footer, remaining sections/blocks, images marked loading="lazy", fonts. Should not affect TBT/FID.
Phase D — Delayed (delayed.js) Starts at least 3 seconds after LCP. Martech, analytics, chat, consent — anything not critical to first paint. Should never block the main thread.

Key Concepts (EDS Ecology)

~2 hrs

Learning outcomes: Navigate the EDS environments, understand the branch → preview → live workflow, and keep every PR at Lighthouse 100.

a. Environments (URLs & Workflow)

  • http://localhost:3000 — local development via aem up
  • https://<branch>--<repo>--<owner>.aem.page — Feature Preview (auto-created per branch, unpublished content)
  • https://main--<repo>--<owner>.aem.page — Prod Preview (main branch, unpublished)
  • https://main--<repo>--<owner>.aem.live — Prod Live (published content)
  • Constraint: <branch>--<repo>--<owner> must be ≤ 63 chars and cannot contain --.
  • Workflow: local → push branch → open PR → PSI check → merge to main → auto-deploy (Code Sync bot).

b. Page Speed (Target: Lighthouse 100)

  • Every PR is auto-tested by the AEM GitHub bot against PageSpeed Insights (mobile scores).
  • Watch LCP (largest contentful paint) and CLS (cumulative layout shift) as primary indicators.
  • Image optimization — use the auto-rendered <picture> tag; never inline raw <img>.
  • Lazy loading — everything below fold goes via lazy-styles.css + loading="lazy".
  • Anti-patterns to avoid: preconnect/preload for non-LCP assets, minification build steps, martech in <head>, second-origin fetches before LCP.
  • Track real-user data via built-in RUM / Operational Telemetry once live.
🧪 Hands-on Lab 4 Open a PR containing your Quote block. Verify the auto PSI comment is ≥ 99 on mobile. Deliberately regress performance (e.g. add a large image without loading="lazy"), observe the failing PSI, then fix it.
